Abstract

Memory is increasingly used in long-horizon agents, yet the net value of building memory over direct retrieval from raw history remains largely unclear. Through a large-scale evaluation across multiple benchmarks and model backbones, we find many dedicated memory systems underperform naive RAG in many cases, indicating a negative net value. Taking RAG as a reference, we dissect the net value of memory into the gains and losses over direct retrieval, termed memory benefit and memory tax.

These gains and losses arise because memory process changes how the raw information is organized and accessed. We view such changes as the double-edged deviations from the raw history. They are originally designed and introduced to benefit the task, for example by reorganizing facts or distilling preferences, but some may also remove or obscure evidence, giving rise to memory tax.

Since memory benefit reflects the expected gains of its design, we then focus more on the overlooked memory tax, study how it arises from the system and evaluation side, and generalize the concept to more application scenarios of memory. We hope the notion of memory tax can provide a new lens and shift more attention from standalone performance to the net value of memory, informing more reliable memory designs and evaluations.

Memory Benefit vs. Memory Tax

A memory system ingests the interaction history into a persistent memory, retrieves memory units for a query, and answers from them. Naive chunk-based RAG keeps the raw history with minimal processing, so it is the natural reference for the net value of building memory.

A per-query comparison with RAG shows memory is not uniformly worse: it solves queries RAG misses, where organization or restructuring helps, while losing queries RAG already solves, where evidence becomes lost, obscured, or harder to access. Both come from the inevitable deviations memory introduces from the raw history.

Net value of memory= Memory Benefit− Memory Tax
Building memory has a dual nature and we call the two sides Memory Benefit and Memory Tax, with their balance defining net value of memory.

Inside the Memory Tax

Memory benefit largely reflects the intended value of a design. We focus on the overlooked side and trace memory tax along three system-side dimensions, plus one evaluation-side factor.

1 · Faithfulness

How well is the information preserved?

We denote the raw turns holding the evidence as gold raw turns and their constructed memory units as gold memory units. Replaying QA with only gold memory units removes retrieval failures, so the remaining tax reflects losses in construction. Tracing sampled atomic facts into memory units shows that information loss does exist in many systems.

2 · Accessibility

How easily can stored information be accessed?

Replaying retrieval for multiple rounds, memory systems recover fewer queries than RAG in the first round: relevant evidence is buried deeper. Case studies show evidence fragmented across units, diluted with unrelated content, or rephrased, which shifts its similarity to the query.

Memory process can reduce evidence accessibility by fragmenting, diluting, or rephrasing it, creating memory tax even when evidence is not lost.

3 · Robustness

How robust is memory across backbones?

We build memory with one backbone and answer with another. With construction fixed, changing the QA backbone causes a larger drop than for RAG in many systems.

Memory process can amplify backbone sensitivity since model-dependent operations add variability to raw history.

+ Benchmark Headroom

The evaluation side makes the tax more visible.

Across more long-term memory benchmarks, simple retrieval already scores high: an IDF-keyword matcher passes 50% on some, and RAG-Hybrid reaches about 70%.

When naive RAG already solves many queries, memory has less room for gains and even modest losses become apparent.

Generalizing Memory Tax

The benefit-tax view is not tied to conversational memory: any nontrivial memory operation can deviate from the source in both directions.

Experiential memory

Agents accumulate experience on training tasks and reuse it on test tasks (Qwen3.5-4B), across embodied (ALFWorld), web (WebShop, Mind2Web), coding (BigCodeBench) and tool use (AppWorld, τ²-Bench). Distilled workflows beat naive trajectory RAG on web tasks, while several memory methods fall behind it on tool use.

World-model memory

For long-horizon scene consistency, directly retrieving and reinjecting past frames stays strong, while latent- or cache-based memories do not consistently beat it.

Design Implications

Simple changes that reduce or compensate for memory tax on existing systems, without a new architecture and without test-time scaling such as deeper retrieval or stronger backbones.

Construction

Make Deviations Recoverable

Keep a lightweight path back to the source: retrieve from raw history alongside memory and rerank them jointly (src-aug). This restores evidence lost in construction or missed in access.

Access

Recursive or Self-Referential Memory

Memory can "remember how it remembers": past queries, evidence and retrieval paths become memory sources (recursive), so evidence found in deep rounds is directly reachable next time.

Beyond Memory Operations

Modeling Future Demand

Between ahead-of-time and just-in-time memory, past interests and access patterns give a prior over what will matter, treating memory as an implicit recommendation system.
